### 原始需求復述（使用者原話）

> 「第一是海洋特效,APP上沒做, 然後全屏畫面感覺很亂, 我想做在一個比較不起眼的位置, 當是小點綴, 然後我想在每次鬧鐘響之前1小時, 像本地鬧鐘一樣, 會提前有一個通知頂欄掛着, 讓用戶知道即將要響.」

### 現況診斷（已確認，不推翻）

1. **Android 其實有海洋**，但 42 格日曆每格 84% 白（`Colors.white.withValues(alpha: 0.84)`，格高 75px × 6 行）壓住，只從格縫漏光 → 使用者體感＝「又亂又似冇做」。**本質係「把全屏海洋收成一個明確小元件」，唔係「補做缺失功能」。**
2. **Web 端**用 `web/index.html` 的 `#oceanBgCanvas` ＋ `ocean_shader.js`（WebGL 光線步進）鋪滿全屏，Dart 層透明穿透 → 同樣「亂」，且與 Android 是兩套實作。
3. **鬧鐘只有「響嗰刻」的通知**，冇前置預告。使用者要的是系統鬧鐘式「提前一小時掛在通知欄」。
4. 附帶問題：README 宣稱 MIT 並連到 `LICENSE`，但倉庫冇此檔；`StatsResult.workHours` 寫死 `workDays * 6`，8 小時班次會算錯。

## 4. 關鍵設計決策

> 每點都有**明確結論**。被否決的方案一併列出原因，方便架構師理解邊界。

### D1. 海洋點綴的放置位置與尺寸 → **日曆下方的細海平線帶（全寬 − 16px，高 56px）**

| 候選 | 描述 | 評估 |
| --- | --- | --- |
| **A（採用）** | 月曆與詳情板之間，一條 56px 高、左右內縮 8px、圓角 16px 的全寬橫帶 | 語意天然（「海平線」本來就係橫的）；只佔屏 6.4%；**不佔 AppBar**（AppBar 已有 5 個動作，塞徽章會擠爆）；Android／Web 可用同一個 Flutter 元件；高度夠畫出天＋海＋太陽三層，仍然「認得出係海」 |
| B | AppBar 內 32px 圓形天色徽章 | 空間零成本，但 32px 圓形內畫唔出「海」，只會變成一粒色點，失去使用者想要的海洋感；且 AppBar 已 5 個動作（導入／今日／‹／› ＋標題），加徽章會令 `390px` 寬下按鈕被壓縮至 <40px 觸控目標 |
| C | 詳情卡片角落 64×64 縮圖 | 只在「已選日期」時存在，使用者 90% 時間（純瀏覽月曆）見唔到，等於冇做；且與 D4「面板打開時隱藏」自相矛盾 |
| D | 保留全屏，只把日曆格改半透明 | 直接違反使用者原話「全屏畫面感覺很亂」；84% 白降到 60% 會令 42 格數字對比度不足（WCAG AA 不達） |

**尺寸理由**：56px 是「足夠畫出天/海/日」與「唔搶主角」的交點。實測 390px 寬下手機，56px ≈ 一個標準 ListTile 的 2/3 高，屬「配件」量級；再細（< 40px）會令 compact 繪製只剩色塊。**唔可以壓縮月曆**：月曆格高固定 75px × 6 行 = 450px 是硬需求，帶插在 `Expanded` 之後，只食掉 `Expanded` 的既有垂直餘裕（390×844 下月曆居中約有 ±90px 餘裕），不改變格尺寸。

### D2. 點綴顯示什麼天色 → **只顯示真實當前時間；唔跟隨選中班次**

**結論**：帶永遠用 `OceanAtmoState.fromCurrentTime()`。現有 `_getCurrentAtmoState()` 的「面板打開 → 用選中班次 startTime」分支，**對海洋部分移除**（詳情卡片的班次 accent 色照舊不動）。

**理由**：
1. **單一語意**。帶是裝飾，裝飾唔應該有兩種解釋。若 22:00 選中「06:00 早更」而帶顯示晨曦，使用者第一反應是「bug」——這正是目前「亂」的來源之一。
2. **衝突無解，所以不要製造衝突**。「跟隨班次」與「反映現在」本質矛盾：一個畫面只有一片海，唔可以同時講兩個時間。
3. 班次天色**已經有**更好的表達載體：日曆格的 `ShiftTokens` 時段色（00–06／06–12／12–18／18–00）。海洋重複一次只是冗餘。

**被否決**：① 純跟隨班次 → 冇選日期時退回真實時間，會令帶在「點一下日期」時突然由星夜變晨曦，閃得刺眼；② 兩者並存（左半現在／右半班次）→ 56px 高度下視覺上會讀成「一條裂開的帶」，且要畫兩套天色，成本翻倍。

**刷新機制**：60 秒 Timer 檢查 `mood`，變才 `setState`。**唔用**每秒 tick（會令 8000ms 波浪動畫被每秒打斷，且無必要）。

### D3. 面板打開時是否隱藏 → **隱藏（200ms 收合至 0 並淡出）**

**理由**：
1. **空間**。面板（`ShiftPickerPanel`／詳情板）打開後 `Expanded` 只剩約 300px，而月曆硬需求 450px+，本身已在擠。再佔 56px 會直接壓到月曆可讀性，違反「不能壓縮月曆可讀性」的硬約束。
2. **焦點**。面板打開＝使用者正在「揀更／睇詳情」，此刻視覺主角應該是面板，唔係裝飾。
3. 隱藏不等於消失：面板關閉即回復，且使用者瀏覽月曆的時間遠多於開面板。

**被否決**：① 收合到 24px 細線 → 24px 內 compact 繪製只剩一條漸變色帶，會被誤讀成「進度條／分割線」，比全隱更差；② 面板半透明覆蓋在帶上 → 面板已有 84% 白底與陰影，疊上去只會更亂。

### D4. Web 端是否保留全屏 WebGL 海洋 → **統一收斂，Web 一併改為 Flutter compact 繪製器**

**結論**：`web/index.html` 移除 `#oceanBgCanvas` 與 `ocean_shader.js` 載入；Web 與 Android 跑同一份 `_OceanPainter`（compact 模式）。`web/ocean_shader.js` 檔案可保留但**不再被引用**，標記為 deprecated，避免一次性刪除帶來回滾風險。

**代價（明講）**：
- Web 失去 WebGL 光線步進的 3D 質感（真折射、真焦散）。但該質感在 56px 高度下**根本睇唔出**——解析度不足以呈現光線步進細節，等於付了 GPU 成本但無視覺回報。
- 需要一次 Web build 驗證（CanvasKit 下 `CustomPainter` 的 `RadialGradient`/`Path` 表現與 Android 一致）。

**換來的好處**：① 兩端視覺同構，唔會出現「手機同電腦唔同樣」的客訴；② 少一個全屏滿幀 GPU 迴圈（Web 端耗電明顯下降）；③ 少一份雙軌維護（每次改天色要改兩處，是既有的債）；④ 少 1 個 JS 檔案載入，令「100% 離線」的宣告更純粹。

**被否決**：保留雙軌（Web 仍用 WebGL，但 canvas 縮成 56px 帶）。原因：要用 CSS 把 canvas 精準定位到 Flutter 佈局算出的位置，`resize`／`safe-area`／`DPI`／捲動都要手動同步，任何一次 Flutter 佈局改動都會令兩層錯位；而且 WebGL 版與 Canvas 版色票本身有差（現有 `_syncWebAtmosphere` 要傳 mood code 校正就是證據），使用者截圖對比會見到明顯色差。維護成本遠高於質感收益。
**Fallback（僅在架構師評估 CanvasKit 於目標瀏覽器有渲染問題時啟用）**：保留 canvas 但改為只覆蓋該 56px 帶，並強制鎖定同一漸變色票常數。

### D5. 預告提前量 → **固定 60 分鐘，不設可配置**

**理由**：
1. 使用者原話就是「提前1小時」，需求明確，唔需要猜。
2. 加設定項要改設定頁＋`shared_preferences` 新 key＋舊資料遷移＋設定頁 UI 文案，成本遠大於收益，且違反「小點綴」的輕量原則。
3. 固定值令驗收可寫成硬條件（「08:00 收到」），可測、可回歸。

**被否決**：① 可配置 5/10/15/30/60/120 分鐘 → 每加一個選項，測試矩陣乘一次；② 跟隨鬧鐘本身的 `offsetMinutes`（例如鬧鐘已提前 30 分鐘，預告再提前 60 分鐘 = 提前 90 分鐘）→ 會出現「提前 90 分鐘預告一個提前 30 分鐘的鬧鐘」這種使用者無法理解的疊加，語意混亂。**規則改為：預告時間恆等於「該鬧鐘實際觸發時間 − 60 分鐘」**，與鬧鐘自己的 offset 無關（offset 已反映在觸發時間裡）。

### D6. 預告通知的形態 → **獨立頻道、`IMPORTANCE_DEFAULT`、ongoing（划唔走）、有提示音、不震動、附「知道了」**

| 決策點 | 結論 | 理由 |
| --- | --- | --- |
| 頻道 | 新增 `pre_alert_channel`，名「響鬧預告」 | **唔可以**重用 `gentle_alarm_channel`（該頻道是 `IMPORTANCE_HIGH` + 震動，是「響嗰刻」用的）。混用會令使用者無法在系統設定裡單獨關掉預告，亦會令「只通知」鬧鐘的語意被污染 |
| 重要性 | `IMPORTANCE_DEFAULT` | 要「頂欄掛着」但**唔應該**像鬧鐘一樣彈 heads-up 搶屏。DEFAULT = 有聲、出現在通知欄、不彈出，正好對應「提前知道」而非「即刻處理」 |
| ongoing | **是**（`setOngoing(true)`） | 使用者原話「頂欄掛着」＝持續可見。若可划走，手一滑就失去提醒作用，功能等於失效 |
| 可清除性 | 附「知道了」action；**鬧鐘觸發時自動取消**；取消鬧鐘時一併取消 | 解決 ongoing「划唔走好煩」的副作用，仍然保留使用者主動 dismiss 的出口 |
| 響鈴震動 | 一次預設提示音、**不震動** | 提前一小時震機＝騷擾；提示音足以令留意到（且使用者可自行在系統頻道設定調整） |
| 點擊 | 開 App（P0）；跳到該日期（P2） | 現有 `MainActivity` 只支援「開 App + `launch_source`」，加日期深層連結要改 Intent 契約，列 P2 |
| id 命名空間 | **必須獨立**，建議 `id + 900000`（`id = YYYYMMDD*10 + index`，最大約 2 026 123 199，加 900 000 = 2 027 023 199 < `Int.MAX`，至 2147 年前安全） | 現有全屏鬧鐘與只通知鬧鐘已共用同一數字 id（靠不同 Receiver 區分）。預告是**第三條**通道，通知 id 與 PendingIntent requestCode 都要另開空間，否則會覆蓋或誤 cancel |

### D7. 同一日多個鬧鐘的預告 → **各自一條，並列不合併（P0）；> 3 條才合併（P2）**

**理由**：
1. 不同鬧鐘的 `label` 語意不同（「開工打卡」vs「收工」），合併會令文案含糊成「今日有幾個鬧鐘」，失去「邊個仲有 1 小時響」的關鍵資訊。
2. 實測絕大多數日子只有 1–2 個 enabled 鬧鐘（每班上限 10 個是上限不是常態），並列唔會洗版。
3. 合併需要額外的聚合狀態機：任一條被 cancel／改更時要重算聚合結果，是幽靈通知的高發區。P0 唔值得為邊緣情境引入這個複雜度。

**但**：因為每條預告都獨立 id、獨立 PendingIntent，**取消與重排天然是逐條的**，這正好令 D6 的生命週期同步（P0-9）變得簡單可靠。

**P2 兜底**：> 3 條時合併成「今日 N 個鬧鐘即將響」，只在實測出現洗版時才做。

### D8. 距現在不足 60 分鐘 → **不發，亦不補發**

**結論**：`leadAt = triggerAt − 60min`。若 `leadAt <= now`，該鬧鐘**不排預告**。

**理由**：
1. 若照樣發，使用者在 08:30 排 09:00 班會**即刻**收到「仲有 1 小時響」——文案與事實不符（實際只有 30 分鐘），是明顯的錯誤訊息。
2. 此刻使用者正在 App 內操作，剛親手排完班，看得到詳情板上的時間，通知屬多餘騷擾。
3. 「不補發」：`leadAt` 已過而使用者才首次開 App，同樣不補。因為補發只會發出一條時間已錯的訊息。**寧可唔發，唔好發錯。**

**被否決**：① 改文案為「仲有 X 分鐘響」並照發 → 需要額外分支與文案，且與 D5「固定 60 分鐘」的簡潔性衝突；② 延後到 `now + 1min` 發 → 使用者剛閂 App 就被通知叫返出嚟，體驗極差。

### D9. 工時統計口徑 → **按實際班時、以分鐘累加、顯示到分鐘**

| 子決策 | 結論 | 理由 |
| --- | --- | --- |
| 時長公式 | `end − start`；`end <= start` → 視為跨午夜 `+24h`；`end` 空 → 360 分鐘；`end == start` → 0 分鐘 | 18:00–00:00 必須是 6 小時而非 −18 小時；`end == start` 若當 24 小時會令「填錯時間」變成 24 小時幽靈工時，寧可顯示 0 讓使用者發現 |
| 跨午夜班歸屬 | 計入**開工日** | 與現有 `slotIndexForTime(startTime)`、`computeStats` 的「同一日只計一次」口徑一致，唔改既有統計語意 |
| 是否四捨五入 | **不四捨五入**，以分鐘累加後格式化 | 四捨五入會累積誤差：每更 6.5h 若捨成 7h，20 更就差 10 小時。以分鐘為單位的整數運算零誤差，只在**顯示**時格式化 |
| 顯示格式 | 「X 小時 Y 分」；Y=0 → 「X 小時」 | 避免「136.5 小時」這種小數，亦避免「137 小時」的假精確 |
| `workHours` 欄位 | 保留為 `totalMinutes ~/ 60`（向下取整），新增 `totalMinutes` 為單一真相來源 | 令既有測試與呼叫點不會因型別改變而爆；新邏輯全部走 `totalMinutes` |
| 未設 `endTime` | fallback 360 分鐘，並在 UI 以 `*` 標註（P1-4） | 相容既有資料（可能有人從未設過收工時間）；標註令使用者知道這是估算值 |

## 8. 給架構師的重點提示（非需求，僅供評估）

1. **改動面**：`calendar_screen.dart`（移除 535-543 全屏、加帶）、`ocean_atmosphere.dart`（compact 模式＋移除 `kIsWeb` 跳過分支）、`web/index.html`（移 canvas／script）、`alarm_service.dart`（預告排程）、`alarm_bridge.dart`（新增 `schedulePreAlert`/`cancelPreAlert`）、`AlarmScheduler.kt`（新頻道＋新 Receiver）、`stats.dart`（`totalMinutes`）、`stats_screen.dart`（顯示格式）。
